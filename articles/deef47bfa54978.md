## はじめに

ProtobufやgRPCは歴史的背景みたいなものがけっこうあると思っていて、加えて言語に依存しない開発を可能とするというメリットの反面言語ごとに実装内容やサポート内容が微妙に異なるといった問題もあり、公式ライブラリとサードパーティー製のライブラリが混在しているのも混乱の元になっているみたいな印象を筆者は持っています。

さらに、Protobufスキーマからコード生成するためのprotobufコンパイラには長らく`protoc`が使わていたと思いますがこれがいまいち使いづらいというか決して開発体験の良いものではなかったと思います。

そんなProtobufまわりの開発体験を大幅に改善してくれたのが[Buf](https://buf.build/)です。Bufが何をしてくれたかというと大きく**Buf CLI**と**Connect Protocol**と**BSR**の3つでしょう。本記事ではこれらの詳しい解説はしませんが興味がある方は以下を参照ください。

https://zenn.dev/jy8752/books/33743f8091c39d

また、Protobufスキーマのバリデーションとしてもともと`protoc-gen-validate`が使われていましたが現在、これもBufがメンテナンスを引き継いで[protovalidate](https://github.com/bufbuild/protovalidate)として開発をしています。(protovalidateについても以前解説本を書いたので興味がある方はこちらも参照ください。)

https://zenn.dev/jy8752/books/84cffcdb89d109

現状、こういったBufエコシステムをフル活用して開発をするのが最も開発体験の良いモダンな開発となるはずだと筆者は考えているため、Rustでどこまで使えるのか検証したいというのが本記事のモチベーションです。

つまり、RustプロジェクトでBuf CLIは使えるのか？Connectやprotovalidateは使えるのか？といったことを検証したいという記事です。

## Connectとprotovalidateについて

コードを書いていく前に先に言うとConnectとprotovalidateの**Rustサポートは現状ありません**。Connectに関してはGoとNodeのみが対応しており他の言語サポートの要望はissueとして上がっていますがおそらく対応予定は直近ではないでしょう。(今見たらpythonのConnect実装が存在していたので近々pythonは公式対応としてアナウンスがあるかもしれません。)

https://github.com/orgs/connectrpc/discussions/7

上記ディスカッションにて[axum-connect](https://github.com/AThilenius/axum-connect)というリポジトリが紹介されていました。ディスカッションの内容を見るとRustのProtobuf対応にはそれなりに苦痛を伴うような内容があるようで、現状積極的な動きにならないのはそれが理由らしい。とはいえ、RustによるConnect対応を待つユーザーはそれなりにいるようです。現状、Webフロントとやり取りをするRustのProtobufによるサーバーを実装したい場合、tonic-webによるgRPC-webによるサーバーを実装するのがベターっぽいですが紹介されていたaxum-connectというライブラリを使えばaxumベースでConnectサーバーを実装することができるかもしれません。これについてはいつか検証してみたいなと思います。

protovalidateに関しても以下のようにissueは上がっていますが現状対応予定はないようです。

https://github.com/bufbuild/protovalidate/issues/33

非公式で対応しているライブラリとして以下のようなものがあるようです。

- [protoc-gen-prost](https://github.com/neoeinstein/protoc-gen-prost?tab=readme-ov-file)
  - これはprotoc-gen-validateというモジュールはあるものの実装は空でした
- [prost-validate](https://github.com/linka-cloud/prost-validate)
  - これはprotovalidateではなくその前のprotoc-gen-validateのRust製のライブラリ。
  - protovalidate対応の話も議論されていたがリフレクションによるパフォーマンス影響を問題視しているようだった。
- [protocheck](https://github.com/Rick-Phoenix/protocheck)
  - これは完全ではないもののprotovalidateに対応している。
  - つまりcelで書かれたバリデーションに対応している。

まだ、デファクトのようなものはないためプロダクションで採用するのは難しいかもしれないが、バリデーションロジックを導入したい場合は検討してもいいかもしれない。本記事では参考までにprotocheckを使った実装例をおまけで載せておきます。

このように、ConnectもprotovalidateもRust対応を期待する声はあるものの現状対応予定はなく、対応するとしてもまだ時間がかかることが予想されます。

ということで、本記事ではtonicを使ったgRPCサーバーの実装とおまけで非公式ではありますがprotovalidateを使ったバリデーションの実装をしていきたいと思います。

## Protobufモジュールの作成

Connectの対応はなくてもBuf CLIはprotobufの開発をする上で非常に便利なツールです。インストールしていない方はインストールしておきましょう。

```bash
brew install bufbuild/buf/buf
```

protobufモジュールを作成するのに一旦設定ファイルである```buf.yaml```を作成しておきます。

```bash
buf config init
```

作成できたら以下のように変更します。

```yaml:buf.yaml
# For details on buf.yaml configuration, visit https://buf.build/docs/configuration/v2/buf-yaml
version: v2
modules:
  - path: proto
lint:
  use:
    - STANDARD
breaking:
  use:
    - FILE
```

変更できたら以下のように簡単なスキーマを作成します。

```bash
mkdir -p proto/weather/v1
touch proto/weather/v1/weather.proto
```

```protobuf:proto/weather/v1/weather.proto
syntax = "proto3";

package weather.v1;

service WeatherService {
  rpc GetWeather(GetWeatherRequest) returns (GetWeatherResponse);
}

message GetWeatherRequest {
  string city = 1;
}

message GetWeatherResponse {
  enum Weather {
    WEATHER_UNSPECIFIED = 0;
    WEATHER_SUNNY = 1;
    WEATHER_CLOUDY = 2;
    WEATHER_RAINY = 3;
    WEATHER_SNOWY = 4;
  }
  Weather weather = 1;
}
```

## ProtobufからRustコードを生成する

GoやTSであれば`buf.gen.yaml`を作成して、`buf generate`すれば良かったりしますがRustの場合、というよりtonicの場合は`build.rs`を作成して`cargo build`でコードを生成するのが一般的だったようです。しかし、以下でアナウンスがあるように`prost`と`tonic`によるコード生成を行うprotocプラグインおよびBSRへのリモートプラグインの対応が現状されているようです。

https://buf.build/blog/bsr-generated-sdks-for-rust

とはいえ、多くのサードパーティー製のRustクレートは`build.rs`でコード生成をおこなうときにいろいろ処理を挟んでいるため、そういったクレートを使用する場合は`build.rs`でコード生成をおこなう必要があるかもしれません。

が、protocプラグインをリモートで使用してコード生成するのが一番手間はないはずなのでそのやり方を紹介します。(build時の依存関係の管理やbuild.rsの作成、tonicであれば内部的にprotocを使うため開発マシンにprotocを入れておく必要があったりするためそういった管理が全て必要なくなる、はず。)

```yaml:buf.gen.yaml
version: v2
plugins:
  - remote: buf.build/community/neoeinstein-prost:v0.5.0
    out: gen/src
    opt:
      - compile_well_known_types
      - extern_path=.google.protobuf=::pbjson_types
  - remote: buf.build/community/neoeinstein-tonic:v0.5.0
    out: gen/src
    opt:
      - compile_well_known_types
      - extern_path=.google.protobuf=::pbjson_types
```

他の言語でgRPCサーバーの実装をしたことがある方はわかると思いますが`neoeinstein-prost`でMessage型のコード生成を行い、gRPCのサーバー/クライアントコードを`neoeinstein-tonic`で生成しています。

## tonicを使ってgRPCサーバーを実装する

### Serviceの実装

生成できたら以下のようにコードを実装します。とりあえず、一旦コード全体を載せておきます。

```rust:src/weather.rs
use rand::prelude::IndexedRandom;
use tonic::{Request, Response, Status};

use proto::v1::{
    GetWeatherRequest, GetWeatherResponse, weather_service_server::WeatherServiceServer,
};

mod proto {
    pub mod v1 {
        tonic::include_proto!("weather.v1");
    }
}

pub struct WeatherService;

impl WeatherService {
    pub fn new() -> Self {
        Self
    }
}

impl Default for WeatherService {
    fn default() -> Self {
        Self::new()
    }
}

#[tonic::async_trait]
impl proto::v1::weather_service_server::WeatherService for WeatherService {
    async fn get_weather(
        &self,
        request: Request<GetWeatherRequest>,
    ) -> Result<Response<GetWeatherResponse>, Status> {
        // ランダムな天気を生成
        let weathers = [
            proto::v1::get_weather_response::Weather::Sunny,
            proto::v1::get_weather_response::Weather::Cloudy,
            proto::v1::get_weather_response::Weather::Rainy,
            proto::v1::get_weather_response::Weather::Snowy,
        ];
        let weather = weathers.choose(&mut rand::rng()).unwrap();

        Ok(Response::new(GetWeatherResponse {
            weather: (*weather).into(),
        }))
    }
}

pub fn get_service() -> WeatherServiceServer<WeatherService> {
    WeatherServiceServer::new(WeatherService::new())
}
```

重要なところは以下の生成コードを読み込むところでしょう。

```rust
use proto::v1::{
    GetWeatherRequest, GetWeatherResponse, weather_service_server::WeatherServiceServer,
};

mod proto {
    pub mod v1 {
        tonic::include_proto!("weather.v1");
    }
}
```

これどのようにモジュール宣言するのが良いのか悩みましたが、とりあえず実装ファイル内にこのように宣言してます。このように宣言することでこのファイル内で生成したコードをuseで読み込んで使えるようになります。

あとはstructに生成されたサービスtraitを実装するだけです。

### サーバーの起動

サーバーの起動は以下のようなコードで実行できます。

```rust:main.rs
#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    tracing_subscriber::fmt::init();

    let addr = "127.0.0.1:3000".parse().unwrap();

    let greeter = MyGreeter::default();
    let greeter = tower::ServiceBuilder::new()
        .layer(tower_http::cors::CorsLayer::new())
        .layer(tonic_web::GrpcWebLayer::new())
        .into_inner()
        .named_layer(GreeterServer::new(greeter));

    println!("GreeterServer listening on {addr}");

    Server::builder()
        // GrpcWeb is over http1 so we must enable it.
        .accept_http1(true)
        .add_service(greeter)
        .serve(addr)
        .await?;

    Ok(())
}
```

重要なところだけ説明するとまず今回はgrpc-webを使うのでlayerに`GrpcWebLayer`を追加する必要があります。加えて、HTTP/1.1を受け入れる必要があるため`accept_http1(true)`を追加して有効化します。こうすることで、Connectサーバーを実装しなくてもgRPC-webと通常のgRPCサーバーの両方に対応したサーバー実装が可能となっています。

:::message
説明が漏れましたがgRPC-webはwebフロントからは直接サーバーにつなぐことはできず、envoyなどでプロキシサーバーを立てる必要がありました。これがwebフロントでProtobufが採用されない大きな理由の一つだと思っていますがConnectによりプロキシサーバーが不要となりました。これはConnectがプロキシサーバーでやっていた処理を実装しなおしたため可能となったことです。tonicはConnectではありませんがConnectと同じようにプロキシサーバーで行っているような処理を実装しているため、envoyのようなプロキシサーバーは不要でgrpc-webが使えるようになっています。tonicすげー
:::

あとは先ほど実装したServiceをadd_serviceで追加するだけです。ここもServiceの実装が増えるたびにadd_serviceを追加していく必要があるためなんかいい感じの実装考えたんですが良い実装が思いつかなかったので良い実装の仕方があったらコメントください。

### サーバーリフレクション対応

gRPCサーバーの実装ができましたが、grpc-webのプロトコルで疎通確認するのは少し面倒なのでgrpcurlのようなgRPCクライアントを使って疎通確認します。gRPCクライアントを使ってリクエストする場合、protoファイルの指定をしなくてもリクエストできるようになるためサーバーリフレクション対応をすると開発効率が上がります。

サーバーリフレクション対応をするにはFileDescriptorSetを直接指定する必要があるため`protoc-gen-prost`にオプションを追加します。

```diff yaml:buf.gen.yaml
version: v2
plugins:
  - remote: buf.build/community/neoeinstein-prost:v0.5.0
    out: gen/src
    opt:
      - compile_well_known_types
      - extern_path=.google.protobuf=::pbjson_types
+      - file_descriptor_set
  - remote: buf.build/community/neoeinstein-tonic:v0.5.0
    out: gen/src
    opt:
      - compile_well_known_types
      - extern_path=.google.protobuf=::pbjson_types
```

このオプションを追加することでFileDescriptorSetが各生成ファイルに含まれるようになります。あとはこのFileDescriptorSetを指定してリフレクションを有効にするだけです。

```rust:main.rs
#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let addr = "127.0.0.1:50051".parse().unwrap();

    let weather_service = WeatherServiceServer::new(WeatherService::new());
    let reflection_service_v1 =
        get_reflection_service_v1(proto_gen::weather::v1::FILE_DESCRIPTOR_SET)?;

    let server = Server::builder()
        .add_service(weather_service)
        .add_service(reflection_service_v1)
        .serve(addr);
    server.await.unwrap();

    Ok(())
}

fn get_reflection_service_v1(
    fd_set: &[u8],
) -> Result<
    tonic_reflection::server::v1::ServerReflectionServer<
        impl tonic_reflection::server::v1::ServerReflection,
    >,
    Box<dyn std::error::Error>,
> {
    tonic_reflection::server::Builder::configure()
        .register_encoded_file_descriptor_set(fd_set)
        .build_v1()
        .map_err(Into::into)
}
```

これでサーバーを起動して疎通確認をしてみます。

```bash
cargo run
```

```bash
grpcurl -plaintext -d '{"city": "tokyo"}' localhost:50051 weather.v1.WeatherService.GetWeather
{
  "weather": "WEATHER_RAINY"
}
```

protoファイルを指定することなくリクエストを投げることができました！ちょっとサービスの数が増えたときにadd_serviceを追加していくのが冗長な気がするので実際はもっと良い感じの実装にしたいところです。

:::message
サーバーリフレクションはv1とv1alphaの２つのバージョンが存在します。gRPCクライアントによってはv1alphaまでしか対応していない場合たあるため、その場合はv1とv1alphaの両方追加するなどして対応することも可能です。
:::

## protovalidateを使ってみる(おまけ)

前述したようにprotovalidateは現状Rustをサポートしていませんが、Protobufを使ってスキーマ駆動開発をする場合、Protobufにバリデーションロジックを記載することができるのは非常に有益だと筆者は考えています。というのも、真面目にスキーマ駆動開発をしようとするとProtoファイルが唯一の仕様書となってくるためここにバリデーションロジックを記載することでより制度の高いAPI仕様書となりえるからです。

ただないものはしょうがないので現状使えるサードパーティー製のクレートを使ってRustでprotovalidateを使う雰囲気だけ紹介します。今回はprotocheckというクレートを使ってみます。

https://github.com/Rick-Phoenix/protocheck

とりあえず、サンプルのスキーマ定義にバリデーションを追加します。

```diff protobuf:proto/weather/v1/weather.proto
syntax = "proto3";

package weather.v1;

import "buf/validate/validate.proto";

service WeatherService {
  rpc GetWeather(GetWeatherRequest) returns (GetWeatherResponse);
}

message GetWeatherRequest {
-   string city = 1;
+   string city = 1 [(buf.validate.field).string = {
+     in: [
+       "tokyo",
+       "osaka"
+     ]
+   }];
}

message GetWeatherResponse {
  enum Weather {
    WEATHER_UNSPECIFIED = 0;
    WEATHER_SUNNY = 1;
    WEATHER_CLOUDY = 2;
    WEATHER_RAINY = 3;
    WEATHER_SNOWY = 4;
  }
  Weather weather = 1;
}
```

スキーマが更新できたらprotocheckクレートを追加します。protocheckは`build.rs`を作成して`cargo build`するのでビルド依存の方にも追加します。

```bash
cargo add protocheck
cargo add --build protocheck
```

追加できたら`build.rs`を以下のように作成します。

```rust:build.rs
use protocheck_build::compile_protos_with_validators;
use tonic_prost_build::Config;

// ref: https://github.com/Rick-Phoenix/protocheck-tonic-svelte-example/blob/main/server/build.rs
fn main() -> Result<(), Box<dyn std::error::Error>> {
    println!("cargo:rerun-if-changed=proto/");

    let out_dir =
        std::path::PathBuf::from(std::env::var("OUT_DIR").expect("Could not find OUT_DIR"));
    let final_descriptor_path = out_dir.join("tonic_descriptor.bin");

    let mut config = Config::new();
    config
        .file_descriptor_set_path(final_descriptor_path.clone())
        .bytes(["."])
        .out_dir(out_dir.clone());

    let proto_include_paths = &["proto"];

    let proto_files = &["proto/user/v1/user.proto", "proto/weather/v1/weather.proto"];

    compile_protos_with_validators(
        &mut config,
        proto_files,
        proto_include_paths,
        &["user.v1", "weather.v1"],
    )?;

    // Compile protos
    tonic_prost_build::configure()
        .build_client(false)
        .compile_with_config(config, proto_files, proto_include_paths)?;

    // Set the env for the file descriptor location
    println!(
        "cargo:rustc-env=PROTO_DESCRIPTOR_SET={}",
        final_descriptor_path.display()
    );

    Ok(())
}
```

tonic-buildを使ったコード生成はだいたい上記のようなコードになるかと思いますが、ビルドする前にprtocheckによる処理を挟んでいる感じです。これでバリデーション可能なtonicの生成コードが得られます。

`tonic::Request`に`validate()`が生えているはずなのでそれを使って以下のようなバリデーション処理を実装します。

```rust:src/validate.rs
use std::future::Future;

use bytes::Bytes;
use prost::Message;
use proto_types::Status as GrpcStatus;
use protocheck::ProtoValidator;
use tonic::{Code, Request, Response, Status};

pub async fn execute<T, F, Fut, R>(req: Request<T>, handler: F) -> Result<Response<R>, Status>
where
    T: ProtoValidator,
    F: FnOnce(Request<T>) -> Fut,
    Fut: Future<Output = Result<Response<R>, Status>>,
{
    if let Err(violations) = req.get_ref().validate() {
        let status_inner: GrpcStatus = violations.into();

        let status = Status::with_details(
            Code::InvalidArgument,
            "Validation Error",
            Bytes::from(status_inner.encode_to_vec()),
        );

        return Err(status);
    }

    handler(req).await
}
```

使用イメージは以下のような感じ。

```rust
#[tonic::async_trait]
impl proto::v1::weather_service_server::WeatherService for WeatherService {
    async fn get_weather(
        &self,
        request: Request<GetWeatherRequest>,
    ) -> Result<Response<GetWeatherResponse>, Status> {
        validate::execute(request, |_| async {
            // ランダムな天気を生成
            let weathers = [
                proto::v1::get_weather_response::Weather::Sunny,
                proto::v1::get_weather_response::Weather::Cloudy,
                proto::v1::get_weather_response::Weather::Rainy,
                proto::v1::get_weather_response::Weather::Snowy,
            ];
            let weather = weathers.choose(&mut rand::rng()).unwrap();

            Ok(Response::new(GetWeatherResponse {
                weather: (*weather).into(),
            }))
        })
        .await
    }
}
```


## Connectってどうなん？(おまけ)

:::message
ここからは個人的な感想であり、ただのポエムです。
:::

Protobufを使ったgRPCサーバーは主にマイクロサービス間の通信用途で採用されるか、モバイルクライアントとサーバー間の通信、特に高トラフィックを捌くゲームサーバーなどで採用されているケースが多かったように感じます。grpc-webが出たことでwebフロントとサーバー間の通信にも利用できるようになったとはいえ、envoyのようなプロキシサーバーを必要したり、馴染みのないプロトコルを使ってまで採用するモチベーションはなかったんじゃないかなと思いますし、少し前はGraphQLのほうがフロントにとってたぶん嬉しかったうえにスキーマ駆動開発が実現できる通信手段だったんじゃないかなと思います。

最近ではNext.jsのサーバー活用の幅がかなり広がったこととHonoのような軽量サーバーフレームワークが流行っていることで普通にfetchするだけで十分な雰囲気を感じます。とはいえ、一人で開発しているならともかくチーム開発をしているならばAPI仕様を定義したくなると思っていてその場合OpenAPIによるRest(ful) APIの採用になるんじゃないかなと思います。

これは完全に個人的な感想ですがOpenAPIの仕様書を書くのがしんどいのといわゆるRestfulなAPIを求められるケースも減ってきたんじゃないかなと思っていてOpenAPI以外のスキーマ駆動開発ができる通信手段がほしいなという気持ちがありました。(TSの実装からOpenAPIの仕様書を生成するみたいなこともたぶんできるんだろうなとは思いますが。)

そこでConnectですよ！Connectならenvoy不要でwebフロントで採用できるのです！
そもそも、筆者が好きなのはgRPCやConnectというよりはProtobufです。Protobufスキーマ言語は学習コストが低い割に表現力が高く、よりコードを書いている感じでスキーマ設計ができます。

zodを使ってTSでスキーマ定義してAPI仕様書吐き出せばええやんと言われればそれはそうでTSに馴染みが深い人がそのような選択をするのはそれはそうよねという感じです。

しかし、Protobufを使ったスキーマ駆動開発という選択肢もあるんだよということが言いたかったです。それを可能としてくれるのがConnectやtonic-webだったりするのです。

- Buf CLI + BSR + tonic-webといった組み合わせが現状RustでProtobufを使ったスキーマ駆動開発をするならベターな選択肢
