## HTTPルーティング

今RustでWeb開発するなら**axum**を使っておくのが良さそう。axumに関しては情報が多く、いろんな人が記事などを書いてくれているのでそちらを参照ください。リポジトリのexampleのコードですが使用イメージは以下のような感じです。

```shell
cargo add axum
cargo add tokio --features macros,rt-multi-thread
```

```rust
use axum::{response::Html, routing::get, Router};

#[tokio::main]
async fn main() {
    // build our application with a route
    let app = Router::new().route("/", get(handler));

    // run it
    let listener = tokio::net::TcpListener::bind("127.0.0.1:3000")
        .await
        .unwrap();
    println!("listening on {}", listener.local_addr().unwrap());
    axum::serve(listener, app).await;
}

async fn handler() -> Html<&'static str> {
    Html("<h1>Hello, World!</h1>")
}
```

ここらへんはGoのechoやTypeScriptのHonoのような軽量なWebフレームワークを使ったことがある人ならそんなに抵抗はないと思います。

## レイヤーアーキテクチャ

現代のWeb開発においてDDDやクリーンアーキテクチャなどを採用している技術スタックに含めている現場はかなり多いでしょう。しかし、これらの開発手法、設計思想に関しては扱う技術者の理解度や経験などによってだいぶ差が出るという印象を持っています。(かなり個人的な意見ですが。)

なので安易にDDDやクリーンアーキテクチャを採用するのはどうかとも思いますが、現代のWeb開発において何のレールもなくWeb開発をするのも現実的ではないので何かしらのレイヤーアーキテクチャやドメインとそれ以外を極力分離して開発するような仕組みは必要というかそれらを望む開発者は多いでしょう。

Railsのような重厚なフレームワークを利用した開発ならまだしもGoのechoやTypeScriptのHonoのように最近は薄めのフレームワークが好まれる傾向もあるのでそういったフレームワークを採用した開発だと何のルールもなくチーム開発をするのはそれなりに難しいと思います。

RustのaxumもRailsのような重厚なフレームワークというよりはHTTPルーティングが中心の薄めのフレームワークのため少なくとも何かしらのレイヤーアーキテクチャを採用すると開発が安定するのではないかと個人的には思います。

幸いにもRustのモジュールシステムはレイヤーを分離し、依存関係の方向性を制御するのにかなり適していると考えられるのでクリーンアーキテクチャのようなレイヤーアーキテクチャを採用したいのであればRustはそれらと相性の良い言語です。

今回は**domain**、**infrastructure**、**usecase**、**handler**の4つのレイヤーに分離してみましたが、特にこの構成が正解とかは思っていなく、それぞれの処理と責務をざっくり分離するとこんな感じの分け方になったというだけでお好きな構成で分離すれば良いと思います。

RustのWorkspace機能を使うことで依存関係の方向を制御することができるようになる。例えば、domainのクレートに依存関係として他のレイヤーのクレートを追加しなければそれらを参照することができない。つまり、domainのレイヤーは他のレイヤーに依存するような実装はできないように強制することができる。

### (余談) package by feature vs package by layer

前述した各レイヤーごとにパッケージ(モジュール)を分ける手法を**package by layer**といったりするようです。逆に機能ごとにパッケージ(モジュール)を分ける手法を**package by feature**といったりするようです。

どっちの方がいいのかという議論はあるみたいですが、どちらかといえばpackage by featureの方が好まれているように感じました。私もファイルを飛び回るよりは関連処理は一箇所にまとまっていてほしいのでpackage by featureの方が良いと思っていました。ここらへんはフロントエンドの文脈だと**コロケーション**という考え方があるようです。

参考

https://www.mizdra.net/entry/2022/12/11/203940

バックエンドにおいても**高凝集**、**疎結合**という考え方に従うとpackage by featureの方が好ましく思えそうです。ただ、Xの議論などを見ていてもpackage by featureを採用したときに**どのようにパッケージを分けるか**はかなり難しい問題だと思いますし、どのような思想で分けるかみたいな話になるので安易にpackage by featureの方がいいだろうとはいえないのではないかと個人的には思います。

Spring Bootのサンプルプログラムの分け方が安易すぎるみたいな意見もありましたね。

https://rshindo.hatenablog.com/entry/2025/11/28/233308

package by featureの場合、ドメインの関心事ごとにパッケージを分けようみたいな話になり、それはDDDやアーキテクチャの話に必然つながりがちです。そして、DDDやアーキテクチャの話になるとどうやってパッケージを分けるかという話は簡単ではなく、それはDDDの文脈で言うなら境界づけられたコンテキストで区切るのか、集約単位で区切るのか、もっと大きな関心事単位で区切るのかみたいな話になる。

DDDやアーキテクチャに強いメンバーがいるならまだしもそういったメンバーがいない中で安易にpackage by featureを採用して苦しむくらいならpackage by layerを採用した方が悩みは少ないかもしれません。

この記事でどっちが良いかという話をする気はないですが盲目的にpackage by featureを採用しても苦しむかもしれないし、package by layerが絶対良くないわけでもないんじゃないかなと個人的には思います。

話をRustに戻して、Rustではworkspace機能を使ってレイヤーごとにクレートを分ければ、依存関係を制御することができるためdomainがinfrastructureに依存するみたいなルール違反を事前に防ぐことが可能です。なので、Rustはそういったレイヤーごとに分離して開発する手法と相性が良いとも言えそうなので今回は素直にレイヤーごとに分けてみました。

#### 値オブジェクト(Value Object)

値オブジェクトとはDDDの文脈で登場するドメインモデルの一種です。本記事で値オブジェクトについて詳細に解説はしませんが値オブジェクトとは一意性を持たない交換可能な値を表現するためのオブジェクトです。逆に一意性を保つオブジェクトはエンティティと呼ばれます。値オブジェクトには例えばユーザーの指名、メールアドレス、IDといったものが考えられます。これをRustで以下のように実装してみました。

```rust
#[derive(Debug, From, Into)]
pub struct UserName(String);

impl UserName {
    pub fn new(name: impl Into<String>) -> Result<Self, Error> {
        let name = name.into();
        if name.is_empty() {
            return Err(Error::InvalidUserName("User name cannot be empty"));
        }
        if name.len() > 100 {
            return Err(Error::InvalidUserName(
                "User name cannot be longer than 100 characters",
            ));
        }
        Ok(Self(name))
    }
}
```

Rustにおいて値オブジェクトを実装するには**タプル構造体**を使った**New Type**パターンが使えそうです。New Typeパターンとは上記のようにタプル構造体を使うことで`UserName`という型でラップした文字列をRust内で扱うことができるようになります。これは新しい型なので他の型と完全に区別して扱うことができるためドメインオブジェクトの定義には持ってこいでしょう。

値オブジェクトはそのオブジェクトを生成する前にバリデーションを通して、不正な値を生成できないようにすることが多いです。Javaのような言語であればコンストラクタを通してでないとオブジェクトが生成できないのでコンストラクタをprivateにしてオブジェクトを生成するにはバリデーション処理を通るファクトリメソッドを使うように強制することが可能です。Rustのような言語では構造体のフィールドに`pub`を付けなければ非公開にすることはできますが同一モジュール内からはアクセス可能なためファクトリ関数を使わずにオブジェクトの生成はできてしまいます。

これに関しては、値オブジェクトには**ファクトリメソッドを必ず定義してそれを必ず使う**といった開発ルール、もしくは静的解析で強制するしかないかもしれません。ただ、そこまでの厳密性を求めなければ十分でしょう。

また、このようなタプル構造体の場合アクセスするには`user_name.0`みたいな取り出し方をしないといけないので以下のような関数を定義する必要があったりする。

```rust
fn into(&self) -> String {
  self.0
}
```

これを毎回実装するのはめんどくさいなと思っていろいろ調べていたら`derive_more`というクレートがあった。

https://docs.rs/derive_more/latest/derive_more/

詳しくはリンクのドキュメントを見てもらいたいのだけど以下のような`From`、`Into`といったderiveマクロが用意されているので、これを使うと自前でgetterみたいな関数を用意する必要がなくなる。

```rust
#[derive(Debug, From, Into)]
pub struct UserName(String);
```

```rust
let user_name: String = UserName::new(name).into();
```

redditでもこれのおかげでnewtype書くのめっちゃ楽になったよ、最高だよって言ってた。

https://www.reddit.com/r/rust/comments/1emi4fi/derive_more_100_released_implement_display_like/?solution=348b663c9016af0a348b663c9016af0a&js_challenge=1&token=bbbe4bf1c9a2b5160829c4be34da5861e99098df20b390b09409001067ac65a9&jsc_orig_r=&tl=ja

#### ドメインエラー

エラーについて話し出すと長くなるので詳細にはここでは書きませんがRustにおいてエラーハンドリングする際に`anyhow`というクレートと`thiserror`というクレートを使うことが多いようです。anyhowはアプリケーションでthiserrorはライブラリにみたいな説明をみたけど雑にエラーをハンドリングするときにはanyhowは便利でちゃんとエラー種別を定義してハンドリングするならthiserrorを使うのが良さそうみたない話だと思う。

で、anyhowとthiserrorはどっちかを使うみたいな話ではなく必要ならどっちも組み合わせて使えばいいみたいな話みたいなのでどっちも使ってみた。具体敵には**ドメインエラーはthiserror**で定義して、それを伝搬させていくのは**anyhow**みたいな感じで使ってみた。これが良いのかどうかはわからないがハンドリングするのって一番外側のレイヤーなことが多くそこまでは雑にエラーを送っていきたいと個人的には思っているのでそのような使い方にはあっていそう。

thiserrorを使ったドメインエラーの定義は以下のような感じ。thiserrorの使い方は公式ドキュメントなどを参照ください。

```rust:domain/src/user/error.rs
#[derive(Debug, thiserror::Error)]
pub enum Error {
    #[error("Invalid user ID. {0}")]
    InvalidUserId(&'static str),
    #[error("Invalid user name. {0}")]
    InvalidUserName(&'static str),
    #[error("Invalid user email. {0}")]
    InvalidUserEmail(&'static str),
}
```

このドメインエラーをanyhowで雑にhandlerまで持っていってハンドリングしたい感じです。これはあくまでRustにおけるエラーハンドリングの一例ですがanyhowとthiserrorを組み合わせることでエラーハンドリングを楽にしつつハンドリングして処理を分岐するみたいなことができるよというお話です。

#### sqlx + SeaQuery

いろいろ調べたがRustにおいては**sqlx**が今のところデファクトっぽい。ただ、sqlxは生のSQLを書く系のクレートなのでORM的な方が好みであれば**SeaORM**といったクレートもあるようです。個人的には**sqlc**がけっこう好きではあるのでRustでも使えるとよかったのだが本記事を執筆している段階では対応していないのでsqlxを使ってみようと思う。

時雨堂さんが作っているらしいのでもし公開されたらRustでもsqlcが使えるかもしれない。

https://voluntas.ghost.io/rust-sql-compiler/

sqlcもそうだが動的クエリを書こうとすると生のクエリを書くよりもORMやクエリビルダーなどの方が楽だったりする。これも調べたところ**SeaQuery**というクエリビルダーのクレートがあり、これをsqlxと組み合わせて使うと良さそうだった。

ということで、DBまわりはsqlxもしくはsqlx + SeaQueryを使うのが良さそうだなという結論に至りました。

#### (余談) sqlxと環境変数

sqlxでコードを書くにあたりquery!を使いたい。理由はsqlxはただの手書きSQLなので構文チェックなどないと容易に誤ったクエリを書いてしまう。sqlxはそのためにマクロを用意してくれており、DBにアクセスしてそのクエリが有効かどうかをチェックしてくれる。これはエディタで書いていてもチェックされ、誤っていれば警告が出る。

ちなみに、オフラインモードみたいなのもあり、事前にファイルにキャッシュとして出力しておけば実際にDBにつながらなくても大丈夫。

今回はオフラインモードは使わずにDBに実際に繋いでもらってsqlxを書こうと思う。

早速、以下のようなエラーが出た。

```shell
set `DATABASE_URL` to use query macros online, or run `cargo sqlx prepare` to update the query cache
```

どうやら、DATABAESE_URLという環境変数が必要なようだ。(DBのアクセス情報ないとつなぎようがないもんね。)

ということで環境変数をセットしたいのだけど開発用の環境変数は移動してきたら勝手にセットされていてほしい。これにはdirenvを使うとできたりする。direnvはdotenvと組み合わせて使うこともできる。

ただ現代のAIを使った開発においてdotenvを使うのはやめようみたいな話もあるし環境変数どう扱うのがいいかなみたいな疑問が出てきた。これに関しては後述するが**dotenvx**と**mise**を使った環境変数の管理、適用をすることでいい感じに開発できるようになった。

```rust:infrastructure/src/db/user.rs
        sqlx::query!(
            "INSERT INTO users (id, name, email) VALUES ($1, $2, $3)",
            id,
            name,
            email,
        )
        .execute(&self.pool)
        .await?;
        Ok(())
    }
    async fn find_by_id(&self, id: &UserId) -> anyhow::Result<Option<User>> {
        let id: Uuid = id.clone().into();
        let row = sqlx::query!("SELECT id, name, email FROM users WHERE id = $1", id)
            .fetch_optional(&self.pool)
            .await?;
        if let Some(row) = row {
            return Ok(Some(User::reconstruct(row.id, row.name, row.email)));
        }
        Ok(None)
    }
}

```

## テスト

Rustのテストはテスト対象のコードと同じファイルにユニットテストとしてテストコードを書くことが多そうですが`tests`ディレクトリに結合テストやE2Eテストを置くこともできるようです。一応簡単な例だけ記載しておくと以下のように`#[cfg(test)]`という属性を付けることでテストコードとして扱われるようになり、慣主的に`tests`というモジュールを宣言してその中にユニットテストを書くことが可能です。

```rust
fn add(a: i32, b: i32) -> i32 {
    a + b
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn add_works() {
        assert_eq!(add(2, 3), 5);
    }
}
```

### テーブル駆動テスト(rstest)

JavaのJUnitにおいてParameterizedTestというテストの書き方を教えてもらったときはひどく感動したのを覚えています。GoのテストでもTableDrivenTestというテストの書き方が推奨されていたりしますがRustでもそのようなテーブル駆動テストを書きたいものです。Rustでテーブル駆動テストを書くには**rstest**というクレートを使うことで実現できそうです。

```rust
    #[rstest]
    #[case("")]
    #[case("alice")]
    #[case("alice@")]
    #[case("@example.com")]
    #[case("alice@@example.com")]
    #[case("alice @example.com")]
    fn ユーザーメール形式が不正ならエラーになる(#[case] email: &str) {
        let user = User::new("Alice", email);
        assert!(matches!(user, Err(Error::InvalidUserEmail(_))));
    }
```

詳しい使い方は今回は省略しますがテスト対象に渡したい入力値をデータテーブルとして事前に定義しておいて、それらを網羅的にテストすることができているのがわかると思います。これをよりエッジケースなどを含み網羅しようとするとProperty Based Testingというテスト手法になりますが今回はそこまでは検証しません。

ぱっと見はJUnitのParameterizedTestの書き方に似ているような気もします。rstestには他にも便利な機能がいくつかあるので興味がある方は公式ドキュメントや以下の記事がおすすめです。

https://techblog.paild.co.jp/entry/2024/03/04/142534
