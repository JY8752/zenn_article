# Zennスクラップから記事を作成する

スクラップとリンク先の実装を基に、元資料の意味を保ったZenn記事を作成する。
完成度や文体の再現よりも、事実への忠実さを優先する。

## リポジトリのガイダンスを読み込む

1. リポジトリルートを特定する。
2. `.clienrules` を読む。
3. `docs/writing-style.md` を読む。
4. `references/zenn-format.md` を読む。
5. 記事ファイルを新規作成する前に、渡されたスクラップURLを `articles/` から
   検索する。同じスクラップを参照する記事があれば、その記事を継続して編集する。

筆者プロファイルは表現と構成にのみ使用する。技術的な主張の根拠には使用しない。
筆者の経験、意見、動機、結論を捏造しない。

## 筆者プロファイルを最新に保つ

`docs/writing-style.md` に記録された確認日と参照ファイルを確認する。

より新しい執筆物がある場合は、最低でも次の内容を読む。

- Git履歴とfrontmatterから判断した、最新の公開記事3本
- 作成する記事と同じ題材を扱っている場合は、現在執筆中の記事
- 最新の公開本の設定、導入、代表的な技術章、最終章

繰り返し観察できる特徴だけを `docs/writing-style.md` に反映する。確認日と
参照ファイルを記録する。最近の執筆物では確認できない記述を削除する。弱い根拠から
人格、私生活、技術力、嗜好を推測しない。

## 元資料を収集する

1. 渡されたZennスクラップURLを開き、すべての投稿を時系列で読む。コードブロック、
   画像、返信、訂正、リンク先も確認する。
2. 各主張、コマンド、コード例、結果、不確実な点、URLを整理した非公開の
   情報源一覧を作る。
3. 次の内容を区別して扱う。
   - スクラップ内で実際に検証された結果
   - 仮説、計画、未完了の作業
   - 筆者が明示した意見
   - リンク先のコードだけで確認できる事実
4. スクラップ全体を取得できない場合は作業を止め、内容の提供を依頼する。
   検索結果の断片や一部の抜粋だけで記事を書かない

ユーザーから明示的に依頼されない限り、スクラップ、そのリンク先、成果物の実装を
超えた独自の技術調査をしない。Zennのドキュメントは記事の書式確認にのみ使用する。

## リンク先の成果物リポジトリを調査する

記事の成果物として提示されたすべてのリポジトリを特定する。利用可能なGitHub連携を
使用するか、一時ディレクトリにshallow cloneして調査する。

READMEだけで調査を終えない。執筆時点で確認できるリビジョン、言語と依存関係の
マニフェスト、ディレクトリ構成、関連するエントリーポイント、設定、実装ファイル、
テストを確認する。コード例と実際のファイルパスを対応付ける。

コードベースは実装内容の検証と正確な説明に使用する。スクラップが実装を参照して
いる場合、または説明に必要な場合だけ、コードから確認した詳細を追加する。
スクラップとコードが一致しない場合は差異を保持し、どちらを正とするかユーザーに
確認する。リポジトリを取得できない場合は推測せず、不足している情報を報告する。

## 記事を書く

frontmatterの直後かつ最初の見出しより前に、次のメッセージを文面を変えず必ず配置する。

```md
:::message
この記事は執筆補助に最大限AIを活用していますがパッションは込めたつもりです。
:::
```

1. スクラップから記事の目的と対象範囲を決める。
2. 重複する記録を統合する。因果関係や時系列の意味を変えない範囲で、説明しやすい
   順序に並べ替える。
3. 内容に合う場合は、リポジトリで繰り返し使われている次の構成を採用する。
   - `## はじめに`
   - 導入付近のスクラップURLと成果物リポジトリURL
   - 元資料で裏付けられる場合のみ `## 対象読者`
   - 題材ごとのセクション
   - `## まとめ` または `## おわりに`
4. 元資料に記載されたプロンプト、コマンド、コードを記事へ載せる場合は、原文を
   そのまま引用し、要約や言い換えで置き換えない。最終的な実装を示す場合は、
   調査した成果物リポジトリのコードを使用する
5. 元資料で選択肢、対応機能、手順などが箇条書きや表で列挙されている場合は、
   項目名、順序、グループを保った一覧として記事へ反映する。文章へ要約して
   項目を欠落させない
6. 未検証の案と未完了の結果には、その状態が分かる表現を付ける
7. `docs/writing-style.md` は控えめに反映する。元資料にない決まり文句、絵文字、
   冗談、警告、読者への呼びかけ、個人的な感想を無理に追加しない
8. 元資料にある注意文や警告文を記事へ記載する場合は、太字の注意書きや通常の
   `:::message` ではなく、Zennの `:::message alert` を使用する
9. 記事全体を「です・ます」調へ機械的に均一化しない。同じ丁寧語の語尾を極端に
   連続させず、元資料が口語的で記事の流れに合う箇所では、短い感想、疑問、
   体言止めなどの口語表現を残す。語尾を散らす目的だけで口語や体言止めを増やさず、
   技術説明の明瞭さを損なうほど崩さない

同じスクラップを参照する記事がない場合は、正しいZennのfrontmatterと
`published: false` を設定して `articles/<slug>.md` を作成する。slugには一意な
12〜50文字の英小文字、数字、ハイフン、アンダースコアを使用する。記事を公開しない。

## 品質ゲートを通す

記事を書き終えたら、完成扱いする前に執筆とは分けた検証工程を実行する。執筆時の
メモだけで判定せず、スクラップを先頭から再読し、記事と成果物リポジトリを照合する。

### 非公開の対応表を作る

各スクラップ投稿と、その中の重要な列挙、プロンプト、コマンド、コード、画像、
URLごとに、次の項目を持つ非公開の対応表を作る。対応表はリポジトリへ保存しない。

- 情報源を識別できる見出しまたは要約
- `検証結果`、`仮説・計画`、`筆者の意見`、`コードだけで確認した事実` の分類
- `反映済み`、`統合済み`、`意図的に省略` の判定
- 対応する記事の見出し
- 統合または省略した理由

すべての投稿を判定する。重複や本題に不要な内容は統合または省略してよいが、
理由のない省略や未判定を残さない。

### 忠実性を監査する

記事を主張単位で読み直し、次を確認する。

- すべての技術的な主張を、スクラップまたは調査したコードに対応付ける。
- すべての個人的な記述を、スクラップまたはユーザーの指示に対応付ける。
- 仮説、計画、未確認事項を、検証済みの事実として書かない。
- プロンプト、コマンド、コード、モデル名、バージョン、ファイル名、出力を
  元資料と一致させる。
- 箇条書きと表の項目、順序、グループに欠落や意図しない変更がないか確認する。
- 注意文、画像、URLを必要な位置へ反映し、Zenn独自ブロックを正しく使用する。
- スクラップと成果物のコードが一致しない場合は、その差異を記事で隠さない。
- 根拠のない背景、利点、推奨、因果関係を追加しない。

### 合否を判定する

次の件数がすべて0になるまで、記事を修正して品質ゲートを再実行する。

- 未判定のスクラップ投稿
- 根拠のない主張
- 原文から変わったプロンプト、コマンド、コード
- 欠落した箇条書きまたは表の項目
- 理由のない省略
- 記事で説明していないスクラップとコードの差異

解消できない項目がある場合は完成扱いにせず、内容と理由をユーザーへ報告する。

### 書式とローカルルールを検証する

リンク、frontmatter、見出し階層、コードフェンスのラベル、Zenn独自ブロックを
`references/zenn-format.md` と照合する。

`node_modules/.bin/textlint <article-path>` が存在する場合は実行する。存在しない
場合は `pnpm exec textlint <article-path>` を試す。技術的な意味を変えずに、
重要な指摘を修正する。解決していない元資料の不一致、取得できないリポジトリ、
未完了のセクション、検証の失敗を報告する。
